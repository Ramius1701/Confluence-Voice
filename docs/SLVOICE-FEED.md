# The slvoice mixer feed: can it reach Confluence-Voice?

Assessment, 2026-10-22. Nothing here is implemented.

Upstream OpenSim-Tranquillity is adding a series of voice pull requests (#353 to #358, #362 to #366) built
around a separate spatial mixer, [legion-voice-mixer](https://github.com/JohnLegionH/legion-voice-mixer)
(`janus.plugin.slvoice`), which does the same job as Confluence-Voice. Most of the series' privacy and
moderation features reach that mixer through a **feed**: the region server tells the mixer, per listener,
whom that listener must not hear (`excl`) and whom it hears greyed-out and silent (`mute`). This note
answers whether that feed can reach Confluence-Voice, and what Confluence-Voice would have to do with it.

Sources read:

- #362's code at `67adc9e903` (JohnLegionH/OpenSim-Tranquillity, branch `ngc/voice-visibility`): the
  region module's feed wiring, `JanusPeerCtlBatchSink`, `MixerOnlySwitches`, the dispatcher and the
  JSON-RPC connector.
- #366's documents (`Docs/voice/`, at `e37ca2232e`), especially `mixer-feed-protocol.md`,
  `architecture.md` and `feature-spec.md`.
- legion-voice-mixer's canonical `docs/voice/mixer-feed-protocol.md` at tag `v1.2.0`.

## Answer: yes, the feed can reach Confluence-Voice

Under the JSON-RPC topology (region → `WebRtcVoiceServiceConnector` → Confluence-Voice), the feed is not
blocked by anything on the region side. Three facts decide it:

1. **The switch reads only the region's own config.** `MixerOnlySwitches.DisableOnStockPlugin` turns
   the mixer-only features off when `[JanusWebRtcVoice] PluginName` is the stock AudioBridge. It never
   asks which leaf service is loaded. A region that sets `PluginName = janus.plugin.slvoice` keeps the
   features on, with no Janus anywhere.
2. **The feed goes to whatever URL the region is given.** `InitialiseVisibility` reads
   `JanusGatewayAdminURI`, `AdminAPIToken`, `AdminTimeoutMs` and `JanusGatewayCACertificateFile` from the
   region's own `[JanusWebRtcVoice]` section, and `JanusPeerCtlBatchSink` POSTs to that URL. Point it at
   Confluence-Voice and the feed arrives there.
3. **Room numbers come from Confluence-Voice's own reply.** Each listener's batches are addressed to the
   room recorded from that listener's provision reply (`RecordListenerRoom` reads the integer `room` from
   the response map). The dispatcher returns the leaf's reply unchanged, and the connector returns the
   JSON-RPC `result` object unchanged (`WebRtcVoiceServiceConnector.cs:200`). So if Confluence-Voice adds
   `"room": <int>` to its provision result, the region addresses that listener's batches to that number.
   An agent with no recorded room is left out of the batch (it is not sent to the estate room by
   default), so Confluence-Voice does not have to reproduce the region's own room hash.

### What this does not cover

- **The region side has to exist first.** The feed is generated by #362's region-module code (the
  feeder, matrix, sink and sender). Confluence-OpenSim does not have it yet. #362 is stacked on #345 to
  #358 (about 60,000 lines in all), and Confluence-OpenSim's voice module has diverged from
  Tranquillity's. **Porting that is the larger half of this work, and it belongs in Confluence-OpenSim.**
- **The join capability (#363)** travels in the Janus `join` message, which the JSON-RPC topology never
  sends. Under that topology it does not apply. The region-to-Confluence-Voice link is already
  restricted to the region hosts by `allowed_region_ips`.
- **The position feed (#364)** needs `vis_protocol` 3 and heartbeats, and in this release it only
  observes. It is not needed for `peer_ctl_batch`.
- **Removing someone from a call (#357)** uses the Janus AudioBridge's participant kick. Under the
  JSON-RPC topology there is no path for it, and this note does not cover it.
- **Call-moderation mutes (#357)** may use the feed's `mute` channel when `PluginName` is not the stock
  plugin (`WebRtcVoiceRegionModule.CallModeration.cs` names "the slvoice mixer's mute channel"). If so,
  implementing `mute` also delivers call-moderation mutes. Not verified.

## What implementing `peer_ctl_batch` would take in Confluence-Voice

### 1. The endpoint

- **Route.** The region POSTs a Janus admin envelope to `JanusGatewayAdminURI`:
  `{"janus":"message_plugin","transaction":"…","admin_secret":"…","plugin":"janus.plugin.slvoice","request":{…}}`.
  Today every POST on 9443 is treated as JSON-RPC, so the handler needs a separate path (for example
  `/admin`) or must recognise the `janus` field.
- **Secret.** A new `feed_admin_secret` setting (32 characters or more; the region warns below that).
  Compare it with `admin_secret` and answer a `"janus":"error"` envelope on mismatch.
- **Reply.** HTTP 200 with `{"janus":"success","transaction":<echoed>,"response":{…}}`. The plugin's
  answer goes in `response`; the region does not read anything outside it.
- **Unknown requests.** Answer `{"slvoice":"error","reason":"unknown_request"}` for anything other than
  `peer_ctl_batch` (heartbeats and `peer_pos` only arrive when arming or the position feed is turned on).
- **Size.** Refuse a `request` larger than 65,536 bytes of compact JSON with `reason: too_big`. The
  region already splits rooms to stay under that limit. The current 256 KB body cap is fine.
- **TLS.** The region's admin client validates the certificate. Without
  `JanusGatewayCACertificateFile` it trusts only the system roots, and the CA option never excuses a
  host-name mismatch. The deployed certificate is self-signed with `CN=127.0.0.1`, so an `https://` admin
  URL on the public name would be refused. Two options: serve the feed over plain HTTP on a LAN or
  loopback port (as the admin page does on 9444), or issue a certificate whose name matches and point
  the CA setting at it. Decide this before building.

### 2. Room numbers

- Add an integer `room` to every successful provision result (spatial and multiagent).
- Keep a map from room number to `RoomKey`, so a batch can find its room. A batch for a number not in
  the map answers `{"slvoice":"error","reason":"unknown_room"}`. The region backs off and retries.
- Recommended: compute the number with the region's own `CalcRoomNumber` (djb2 over region id,
  `"local"` and parcel id; or grid id, channel and `"multiagent"`). The region logs its estate room
  number at start-up, so matching numbers make the logs comparable. Any stable positive 32-bit numbers
  also work, because the region only uses what Confluence-Voice returns.

### 3. Per-listener state

For each room, per listener agent id, two independent sets of source agent ids, `excl` and `mute`:

- `op: replace` sets a named listener's set exactly (an empty array clears it). `add` takes a union,
  `remove` subtracts. **Only listeners named in the batch are touched**: there is no room-wide reset,
  and leaving a listener out is never a clear.
- The `excl` and `mute` channels never change each other. On `add`/`remove` an absent `mute` key means
  "no change". On `replace` the region always sends `mute`, even as `{}`.
- **Deferral.** An entry for a listener who has not joined the room yet is held, merged with the same
  op semantics, and applied when that listener joins, before the first roster is built. Count these in
  `deferred_listeners`. The mixer's documentation explains why: the region sends a listener's full
  column when it provisions, which is often before the viewer has joined. A dropped entry would mean a
  banned source is audible until the next change. Cap the store per room and free it with the room.
- Lowercase, hyphenated UUIDs; skip malformed items and count them in `skipped`.

### 4. The mix and the roster

- **Mix** (`room.rs`, `mix_room`): skip a source that is in the listener's `excl` or `mute` set, the
  same way a viewer's own mute (`peer_gain <= 0`) is skipped today. This is enforced in the mix, so a
  modified viewer cannot undo it.
- **Roster** (`build_roster`):
  - An excluded source gets no entry for that listener: no join, no level.
  - A source that becomes excluded gets a leave (`"l": true`, `proto::leave_json`, already used for
    real departures), and is forgotten as announced. If the exclusion is later lifted, it is announced
    again as a join.
  - A muted source stays in the list with `"m": true`. `RosterEntry.moderator_muted` already exists
    and is always `false` today. This makes the viewer grey the participant out.
- One agent can be a listener in more than one room (spatial plus a call). Sets are kept per room.

### 5. The reply

```json
{ "slvoice": "applied", "op": "add", "room": 12345,
  "entries": 3, "mute_entries": 1, "skipped": 0, "deferred_listeners": 0,
  "mixer_instance": "9f2c61d04b7a83e1" }
```

- `slvoice` is `empty` for a valid batch with nothing to apply, and `error` with a `reason` otherwise
  (`unknown_room`, `malformed`, `too_big`).
- `mixer_instance` is a random 16-hex-digit value chosen at start-up. The region uses a change in it to
  notice a restart and send every listener's full column again. That matters here: all of this state
  is in memory and lost when Confluence-Voice restarts.
- `vis_protocol` should be left out, or set to the lowest version actually implemented. Advertising 3
  makes the region start sending `peer_pos`.

### 6. Tests

Reuse the cases the region and the mixer document: op scoping (replace touches only named listeners),
`excl`/`mute` independence, deferral with op-faithful merge (an un-ban sent before the join must not be
replayed as a ban), the leave on exclusion and the join on un-exclusion, the `"m"` flag, the size limit,
and `unknown_room`. The existing `room.rs` tests show the pattern.

## Size

- **Confluence-Voice:** small to medium. One endpoint, a room-number map, two sets per listener with a
  deferral store, a gate in the mix loop, three roster changes and a reply builder. Probably 500 to 800
  lines with tests. No new dependencies.
- **Confluence-OpenSim:** large. #362's feeder, matrix, sink and sender, on top of whatever parts of
  #345 to #358 it needs, ported into a module that has already diverged.

## What it would deliver

With both halves in place and the region set to `PluginName = janus.plugin.slvoice`,
`VisibilityFeederEnabled = true` and `VisibilityEmitEnabled = true`:

- Estate and parcel bans and parcel access lists enforced in voice, not just at provisioning.
- Parcels that hide their avatars ("see avatars" off) hidden in voice too.
- Parcel voice moderation (#362's `VoiceModerationEnabled`): parcel owners, estate managers and group
  moderators can mute someone on their parcel. This is the moderator mute the README roadmap lists
  as needing a new JSON-RPC method. With the feed, no new method is needed.
- Possibly call-moderation mutes from #357 (see above, not verified).
